1 The journey of a workflow run

Every workflow run goes through the same nine stages. Pick a stage, or use the ← → arrow keys.

1 · An event happens

Every run starts with an event: something that happened in your repository. You might have pushed code, opened a pull request, clicked Run workflow, or a scheduled timer went off.

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:   # manual button
  • push: code landed on a branch
  • pull_request: a PR was opened or updated
  • workflow_dispatch: someone clicked a button
  • schedule: a cron timer (in UTC)

Good to know: filters like branches: and paths: decide whether this event should start the workflow at all.

2 · GitHub finds matching workflow files

GitHub looks in .github/workflows/ for YAML files whose on: section matches the event. Every match becomes a separate workflow run.

.github/
└── workflows/
    ├── check.yml    # on: pull_request
    └── deploy.yml   # on: push to main
  • One file = one workflow
  • Many workflows can run for the same event
  • For a push, the file in that commit is used
  • For a pull_request, the file in the PR is used

Good to know: because a PR can change the workflow file, GitHub gives PRs from forks no secrets and a read-only token.

3 · The run is queued

GitHub creates the run and checks concurrency: is another run with the same group name already going? If so, the new run waits, or the old one is cancelled.

concurrency:
  group: pages
  cancel-in-progress: false
  • Same group = never at the same time
  • cancel-in-progress: true cancels the old run
  • false makes the new run wait
  • Never cancel a deploy halfway through

Good to know: cancelling old runs on pull requests saves minutes, because only the newest push matters.

4 · Jobs are scheduled

A workflow contains one or more jobs. Jobs run in parallel unless one needs another. An if: can skip a job.

jobs:
  check:   ...
  build:
    needs: check
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
  • needs = wait for that job to succeed first
  • If a needed job fails or is skipped, this job is skipped too
  • if: ${{ !cancelled() }} runs a job no matter what happened before

Good to know: see section 2 below for a picture of how jobs connect.

5 · Each job gets a fresh runner

A runner is the machine that runs a job. GitHub-hosted runners are brand-new virtual machines that are thrown away after the job. Every job starts with nothing on disk.

runs-on: ubuntu-24.04
permissions:
  contents: read
  • Files don't carry over between jobs
  • The job gets a GITHUB_TOKEN for talking to GitHub
  • permissions: decides what that token may do
  • Start with permissions: {} and add only what's needed

Good to know: that's why most jobs start with actions/checkout: the code isn't there until you fetch it.

6 · Steps run in order

Inside a job, steps run one after another on the same machine, so they share files. A step either runs a shell command (run:) or uses a ready-made action (uses:).

steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-python@v5
    with:
      python-version: "3.12"
  - run: python scripts/check_site.py site
  • ${{ }} is filled in before the shell runs
  • Never put untrusted text (PR titles, commit messages) straight into run:
  • Pass it through env: instead

Good to know: an action runs inside your job with your token. Pin actions to a commit SHA so nobody can swap their code.

7 · Jobs hand off work with artifacts

Jobs don't share a disk, so one job uploads files as an artifact and a later job downloads them. Small values can be passed as job outputs.

- uses: actions/upload-pages-artifact@v3
  with:
    path: site/
  • Artifact: files passed between jobs
  • Cache: speeds up installs, and may be empty
  • Output: a short text value ('true', not true)

Good to know: build once, then deploy that exact artifact. Don't rebuild for each environment.

8 · Environments guard deployments

A job that names an environment must pass that environment's rules before it starts. Rules can be required reviewers, a wait timer, or "only from main". Environment secrets are only unlocked after that.

deploy:
  environment:
    name: github-pages
    url: ${{ steps.deployment.outputs.page_url }}
  permissions:
    pages: write
    id-token: write
  • github-pages is created for you when you turn on Pages
  • By default it only allows deploys from the default branch
  • id-token: write lets the job prove who it is (OIDC). No password is stored

Good to know: the URL you set appears on the run page and under Deployments in the repo.

9 · The result shows up everywhere

Every job reports a check: ✅, ❌ or skipped. These appear on the commit, on the pull request, and in the Actions tab with full logs.

Settings → Rules → Rulesets
  Require status checks:
    ✔ check / gate
  • Branch protection can require a check before merging
  • Require one stable "gate" job, not every matrix job
  • Failed? Read the log, fix, push again, or click Re-run

Good to know: the banner at the top of this page is the result of a real run. Click it to see that run's log.

3 How this page was deployed

This site is plain HTML in the site/ folder. A workflow checks it, packages it, and publishes it to GitHub Pages.

  1. ⬆

    Push to main

    You push a change. The push event matches deploy.yml.

  2. ✔

    check job

    Runs scripts/check_site.py, which fails on broken links or missing files.

  3. 📦

    build job

    Writes build-info.json, then upload-pages-artifact packages site/.

  4. 🚀

    deploy job

    Passes the github-pages environment, then deploy-pages publishes the artifact.

  5. 🌐

    Live

    GitHub serves the files at https://<user>.github.io/<repo>/.

4 Glossary

Workflow

One YAML file in .github/workflows/. Describes when to run and what to do.

Event

What starts a workflow: push, pull request, schedule, manual button…

Job

A group of steps that runs on one runner. Jobs run in parallel by default.

Step

One command (run:) or one action (uses:). Steps run in order.

Action

A reusable, packaged step, like actions/checkout. Pin it to a SHA.

Runner

The machine that runs a job. GitHub-hosted runners are fresh for every job.

Artifact

Files uploaded by one job so a later job (or you) can download them.

Cache

Saved files that speed up installs. The job must still work without it.

Secret

An encrypted value, like an API key. Hidden in logs, but still handle it carefully.

Environment

A named deploy target with rules (reviewers, branches) and its own secrets.

GITHUB_TOKEN

An automatic token for each job. permissions: controls what it can do.

OIDC

Lets a job prove its identity to a service (like Pages or a cloud provider) without a stored password.
